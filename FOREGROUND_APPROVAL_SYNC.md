# SmartMaktab 0.7 · обновление заявок между сеансами

В отдельной локальной песочнице два вошедших пользователя могут наблюдать за одной заявкой без перезагрузки. Например, сотрудник подаёт заявку, директор этой школы видит её в своём окне, а после утверждения сотрудник видит новый статус и план. Стандартный Dev не меняется; в облаке эксперимент недоступен.

## Как это работает

- Видимая вкладка периодически читает текущую роль, очередь и список записей выбранной школы. Интервал — 5 секунд после успешной сверки; запросы выполняются последовательно. При ошибке очередь скрывается до следующей успешной сверки, а интервал чтения очереди увеличивается до 30 секунд. При скрытии вкладки или отключении сети чтение на паузе; при возврате начинается новая сверка.
- На выходе, при смене школы или аккаунта незавершённое фоновое чтение отменяется. Ответ для прежней школы не перерисовывает текущую. RLS по-прежнему отвечает за авторизацию каждого чтения, серверные RPC — за проверку решений.
- Сверка **ничего не отправляет**. Черновик IndexedDB остаётся на том же устройстве до ручной отправки. На текущий экран приходит только состояние сервера; неотправленные заявки не видны в другом сеансе. Автообновление не является push-каналом и не работает для закрытой вкладки.
- Как и прежде, результаты ограничены сотней строк без пагинации. Перечень учреждений не обновляется по таймеру: для новых назначений вне текущей школы используйте «Обновить доступ». При конкурентных решениях сервер допускает только одно; редактирования планов и общего разрешения конфликтов нет.

## Локальная проверка

1. Подготовьте песочницу по [инструкции согласования](PLAN_APPROVAL_EXPERIMENT.md) и настройте `dev/supabase-config.json` с локальным URL и публичным ключом. Включите `"approvalExperiment": true` и `"approvalFollow": true`. `approvalOutbox` нужен только если вы также проверяете локальные черновики.
2. Соберите клиент (`npm run build`). Откройте `http://localhost:4173/dev/` в двух независимых профилях браузера. Используйте тестовые аккаунты `staff-a@example.test` и `director-a@example.test`, без настоящих школьных данных.
3. Подайте вымышленную заявку под сотрудником и утвердите её из другого профиля. Новый статус и план должны появиться без нажатия «Обновить». Для объединённой браузерной проверки со сценарием IndexedDB добавьте `"approvalOutbox": true`, задайте `SM_DEV_CREDENTIALS_FILE` и выполните:

```bash
SM_APPROVAL_EXPERIMENT=1 npm run test:follow:browser
```

Chromium проверяет два независимых сеанса через локальные Supabase Auth и PostgREST, остановку чтения без сети, получение утверждённого плана при восстановлении связи без отправки черновика и остановку опроса после выхода.

**Следующий шаг перед облачным пилотом:** повторить матрицу прав на отдельном облачном Supabase Dev с синтетическими аккаунтами и согласовать роли и обезличивание. Не включайте локальный эксперимент в основном Dev. Полная офлайн-синхронизация, push, шифрованное школьное хранилище и USB-обновление не реализованы.
