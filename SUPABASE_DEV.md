# SmartMaktab · подключение Supabase Dev

**Состояние:** миграция прошла сквозные проверки на локальном PostgreSQL 17.11, Supabase Auth (GoTrue v2.198.0) и PostgREST v16.6. Chromium проверен и с подменой HTTP, и с реальными локальными Auth/Data API. Целевой облачный проект не настроен и не проверен. Не используйте настоящие школьные данные, в том числе в названиях, адресах и паролях тестовых аккаунтов.

## 1. Подготовка отдельного проекта

1. Создайте **пустой отдельный** Supabase-проект для синтетических данных. Не применяйте миграцию на существующую базу и не запускайте старый `supabase/schema.sql`. Если старый SQL уже был применён, подготовьте отдельный чистый проект, а не очищайте существующие таблицы.
2. В настройках Auth включите провайдер Email/Password и отключите публичную саморегистрацию и анонимные входы. Для dev создавайте пользователей вручную в Dashboard, с уникальными тестовыми паролями. Убедитесь, что тестовые аккаунты подтверждены; письма на `example.test` не отправляем. Пароли, токены, `service_role`, `sb_secret_…` и пароль БД не передавайте в чат, Git или frontend.
3. В SQL Editor целиком выполните `supabase/migrations/20261124000100_dev_read_only.sql` от имени владельца схемы (`postgres` в Dashboard). Это первая миграция, не предназначенная для повторного применения. При использовании управляемого CLI вместо Dashboard применяйте её через историю миграций, не обоими способами.
4. В настройках Data API оставьте `public` в списке доступных схем, **не добавляйте `smartmaktab_private`** и не расширяйте выданные миграцией GRANT. Приложение читает через Data API только явно перечисленные столбцы.
5. Создайте и подтвердите тестовые аккаунты `staff-a@example.test`, `deputy-a@example.test`, `director-b@example.test`, `authority-a@example.test`, `developer@example.test`. Для автоматической приёмки создайте и подтвердите шестой аккаунт `no-membership@example.test` без назначения. Один раз выполните `supabase/dev_fixture.sql`: файл привяжет только перечисленные тестовые аккаунты и добавит синтетические учреждения и записи. Сценарий остановится, если один из пяти обязательных аккаунтов не подтверждён.

## 2. Локальный клиент

Из `SmartMaktab_App` (Node.js 20 или новее):

```bash
npm ci
npm run build
cp dev/supabase-config.example.json dev/supabase-config.json
python3 -m http.server 4173 --bind 127.0.0.1
```

В `dev/supabase-config.json` укажите `url` вида `https://<project-ref>.supabase.co` и ключ `publishableKey` вида `sb_publishable_…`. Это **публичный** ключ, не заменяющий RLS. Конфиг не коммитится. Для локального Supabase клиент также принимает `http://localhost:54321` или `http://127.0.0.1:54321` и локальный `anon` JWT (не `service_role`). Откройте `http://localhost:4173/dev/` или ссылку «Supabase Dev» в меню демо. Пока конфиг отсутствует, форма входа скрыта.

Если публикуете dev-контур для команды, раздавайте **только каталог `dev/`** на отдельном HTTPS-адресе, не на origin демо-PWA. Ограничьте доступ к хосту по возможности, добавьте серверный заголовок `Content-Security-Policy: frame-ancestors 'none'` (с сохранением ограничений из HTML) и `Cache-Control: no-store` для HTML страницы входа и конфигурации. В браузере сессия живёт в памяти, а не в `localStorage`/`sessionStorage`. После выхода приложение немедленно очищает список; при сетевой ошибке оно предупреждает, что отзыв на сервере не подтверждён. Отзыв refresh-токена сам по себе не аннулирует уже выданный JWT до его истечения. Отзыв назначения в БД влияет на **последующие запросы**; уже показанные строки нельзя отозвать задним числом. Кнопка «Обновить доступ» заново читает список с сервера.

## 3. Матрица допуска и критерии приёмки

| Кто | Учреждения и записи |
| --- | --- |
| Без входа | Нет доступа к таблицам, нет показанных данных. |
| Аккаунт без назначения | Вход возможен, учреждений и записей нет. |
| Сотрудник A / завуч A / администратор школы A | Только назначенная школа A, без корзины. |
| Директор B | Только назначенная школа B, без корзины. |
| Маориф A | Собственный орган и прямые школы A/A2; школа B недоступна. Иерархия зон пока одноуровневая. |
| Разработчик из приватной таблицы | Метаданные всех учреждений и записей, включая удалённые, плюс серверный аудит через Data API. В интерфейсе — только учреждения и записи; экран серверного аудита отсутствует. |

Для обычных пользователей через Data API доступны только собственные назначения. Для всех аккаунтов, включая разработчика, браузерная запись и изменение ролей запрещены. `payload` закрыт для клиентских ролей. Аудит фиксирует доверенные INSERT/UPDATE/DELETE над учреждениями, назначениями, записями и списком разработчиков, без содержимого записей; он **не** фиксирует чтение, не защищён от владельца БД и не является журналом соответствия требованиям.

Перед закрытием этого dev-этапа повторите проверки на **целевом** Supabase с синтетическими аккаунтами:

- Вход/выход, неверный пароль, перезагрузка без восстановления сессии. Без назначения вход не раскрывает учреждения.
- Сверьте матрицу не только по UI, но и по Data API от имени каждого тестового аккаунта: запрос явного идентификатора школы B от имени A/маориф A не возвращает строк, anon без входа не получает доступ, запись/изменение роли и `payload` получают отказ. Не подменяйте тест клиента проверкой от имени `postgres` или `service_role`.
- В тестовом проекте отзовите назначение и повторите запрос с того же устройства без нового входа: сервер перестаёт возвращать данные для этой роли. Проверьте появление записи в аудите после доверенной правки. Проверку делайте без публикации JWT и без включения чувствительного логирования запросов.

## 4. Автоматическая приёмка через Auth и Data API

`npm run test:live` обращается к endpoint из `dev/supabase-config.json`, входит шестью тестовыми аккаунтами и проверяет матрицу по данным из `supabase/dev_fixture.sql`. Запускайте только на отдельном проекте с **неизменёнными синтетическими фикстурами** и без других назначений: ожидаются точные списки. Тест проверяет настройки Auth, доступ anon, неверный пароль, видимость школ и корзины, запрет чтения `payload` и приватной схемы, запрет записи и отказ при обновлении завершённой сессии. Проверки записи используют пустой INSERT и условия, которым не может удовлетворить ни одна строка. Скрипт не выводит пароли, токены или тела ответов.

Создайте **вне репозитория и каталога любого HTTP-сервера** приватный JSON-файл. Имена полей фиксированы, значения — только пароли синтетических аккаунтов, заданные вами в Dashboard. На Unix ограничьте права файла (`chmod 600`); на Windows предоставьте доступ только своему пользователю. Не передавайте файл в чат, не добавляйте его в архив и не публикуйте.

```json
{
  "staff-a": "",
  "deputy-a": "",
  "director-b": "",
  "authority-a": "",
  "developer": "",
  "no-membership": ""
}
```

```bash
# Из SmartMaktab_App, после npm ci:
export SM_DEV_CREDENTIALS_FILE=/абсолютный/путь/вне/репозитория/test-passwords.json
# Только для отдельного облачного проекта: значение между https:// и .supabase.co
export SM_EXPECTED_DEV_REF=идентификатор_dev_проекта
npm run test:live
```

После успешного прогона отдельно проверьте отзыв назначения: войдите как `staff-a`, из SQL Editor целевого **dev**-проекта удалите только назначение этого тестового пользователя, нажмите «Обновить доступ» в том же сеансе и убедитесь, что список пуст. Убедитесь, что в аудите появился `DELETE` для `public.school_memberships`, затем восстановите тестовое назначение, если планируете повторять тесты. Не копируйте JWT из DevTools и не сбрасывайте базу.

## 5. Повторение локальных проверок

```bash
npm ci
npm run build
npm test                         # PGlite + конфигурация, включая эксперимент
npx playwright install --with-deps --only-shell chromium
# при работающем локальном HTTP-сервере на порту 4173:
npm run test:browser             # Chromium; Supabase HTTP подменён
```

Для локального сквозного прогона можно использовать Supabase CLI v3 с Docker или Podman: из `SmartMaktab_App` выполните `supabase start` (используется готовый `supabase/config.toml`; не запускайте `supabase init` поверх него). Создайте и подтвердите те же шесть аккаунтов в локальном Studio, выполните `supabase/dev_fixture.sql` один раз после миграции, затем настройте публичный локальный ключ и приватный файл тестовых паролей. Для loopback `SM_EXPECTED_DEV_REF` не нужен. При работающем локальном сервере приложения:

```bash
npm run test:live
npm run test:browser:live        # Chromium, настоящий Auth/Data API; только loopback
```

В данной итерации использовались отдельные локальные процессы PostgreSQL, Auth и PostgREST с тестовым шлюзом: Docker и Podman в рабочей среде отсутствовали. Полный запуск контейнерного набора CLI и особенности облачного шлюза в этом прогоне не проверялись.

До школьного пилота отдельно согласовать матрицу прав, минимальный набор данных, правила обезличивания и обратной идентификации, сроки хранения и удаления, доступ/аудит разработчиков и проверяемое восстановление из зашифрованных резервных копий. В стандартном dev-контуре запись и утверждение заявок **отключены**. Отдельно существует [локальный эксперимент создания плана](PLAN_APPROVAL_EXPERIMENT.md), который не входит в базовое развёртывание. Серверное восстановление, синхронизация устройств, USB-обновления и production backup не реализованы. Локальные функции демо не заменяют их.
