# SmartMaktab · прототип согласования создания плана

**Не включён по умолчанию.** Базовое развёртывание Supabase Dev (`supabase/migrations/`) остаётся только для чтения. Этот эксперимент выполняется в отдельной локальной базе с синтетическими данными. Он не меняет основной PWA, не подключает облако и не утверждает реальные школьные полномочия. Экран согласования в основном PWA остаётся локальной демонстрацией. Новый экран подключён к серверным RPC **только в отдельном локальном `dev/`**, при явном включении.

## Правила тестового маршрута

| Действие | Правило в прототипе |
|---|---|
| Создать заявку | `staff` или `deputy` с текущим назначением в той же школе. Разрешено только создание плана; заявку нельзя редактировать. |
| Читать очередь | Автор, если он всё ещё сотрудник или завуч этой школы, и её назначенный директор. Зонный доступ маориф, роль школьного администратора и статус разработчика сами по себе не дают доступа к очереди. |
| Утвердить или отклонить | Директор той же школы, не автор заявки. Если автор утратил право подачи, утверждение запрещено; директор может отклонить. |
| Создать план | Сервер создаёт запись типа `plan` из исходного названия **в той же транзакции**, что и утверждение. Отклонение не создаёт запись. |
| Прямые изменения таблиц | Запрещены всем клиентским ролям. Клиент вызывает только две целевые функции через RPC. |

Аудит фиксирует автора подачи, директора, изменение статуса и создание плана; название заявки в аудит не копируется. Ограничения и блокировки БД обеспечивают одно решение и один план даже при параллельных запросах. Асинхронной очереди, подписей, уведомлений и аудита чтения нет.

## Как повторить проверку

1. Поднимите **отдельный локальный** контур с базовой миграцией и синтетическими фикстурами по [SUPABASE_DEV.md](SUPABASE_DEV.md). При желании сначала запустите базовую проверку `npm run test:live`. Её точные ожидаемые количества записей неприменимы к базе после включения эксперимента.
2. В локальном Auth создайте и подтвердите `director-a@example.test`. Добавьте пароль в тот же приватный файл `SM_DEV_CREDENTIALS_FILE` с ключом `director-a`. Не передавайте пароли или секретные ключи в чат.
3. Один раз примените `supabase/experiments/plan_approval.sql`, затем `supabase/experiments/plan_approval_fixture.sql` как владелец локальной базы. Не помещайте эти файлы в `supabase/migrations/` и не применяйте к основному облачному проекту. Перезапись и очистка данных не нужны.
4. С локальным URL в `dev/supabase-config.json` выполните проверки API и SQL:

```bash
npm test
SM_APPROVAL_EXPERIMENT=1 npm run test:approval:live
```

Сквозной тест запускается только на loopback и оставляет в стенде синтетические заявки и планы с уникальным префиксом `DEV`. Он проверяет Auth, изоляцию очереди, запрет подмены, повторную подачу, параллельные решения, итоговую запись и аудит. Логи теста не содержат паролей или токенов. Локальные тесты для SQL проверяют также запрет самоутверждения после смены роли, отказ после отзыва полномочий и откат неудачного утверждения без ложной записи аудита.

При необходимости остановить запись выполните в песочнице `supabase/experiments/pause_plan_approval.sql`. Он отзывает право вызова обеих функций, **не удаляя** заявки, планы или аудит. Уже выполняющиеся транзакции пауза не отменяет. Действующие правила чтения сохраняются.

## Локальный экран 0.5

1. После подготовки песочницы и применения экспериментального SQL добавьте в локальный `dev/supabase-config.json` поле `"approvalExperiment": true` рядом с URL и публичным ключом. По умолчанию поле `false`; на облачном endpoint или в браузере не на loopback оно игнорируется. Включение интерфейса не выдаёт права БД и не применяет SQL.
2. Выполните `npm run build`, запустите локальный HTTP-сервер на `localhost:4173` со связью только с loopback и откройте `http://localhost:4173/dev/`. Как сотрудник или завуч школы A, подайте заявку с вымышленным названием. Затем войдите как директор A и утвердите или отклоните её. Директор B не увидит заявку, а у маориф и разработчика без прямой роли не появится панель. Утверждение обновит список планов в выбранной школе; подача и отклонение план не создают.
3. При отсутствии серверного ответа форма предлагает повторить **то же** действие. Без отдельно включённого [эксперимента IndexedDB](OFFLINE_OUTBOX_EXPERIMENT.md) параметры и ключ повтора хранятся только в памяти открытой вкладки. При выходе или перезагрузке они исчезают. Если итог неясен после перезагрузки, сначала обновите список заявок и проверьте статус, а не подавайте новую. Панель показывает до 100 последних заявок; пагинация не подключена.

Проверка Chromium с реальными Auth/PostgREST и имитацией потери ответа после успешного выполнения сервером:

```bash
SM_APPROVAL_EXPERIMENT=1 npm run test:approval:browser
```

Она создаёт отдельные синтетические записи. Чтобы скрыть экран, верните флаг в `false`; чтобы остановить запись через RPC, отдельно выполните `pause_plan_approval.sql`.

## Контракт API

- `submit_plan_creation(p_school_id, p_title, p_client_request_id) → UUID`. На одно намерение создаётся один UUID запроса. При неизвестном результате после сетевого сбоя клиент повторяет ровно те же параметры и UUID; совпадающая подача вернёт прежний идентификатор. Изменённые параметры с тем же ключом отклоняются (`23505`, HTTP 409). Название — до 240 знаков.
- `decide_plan_creation(p_school_id, p_request_id, p_approve) → {request_id, status, record_id}`. Повтор того же решения тем же действующим директором возвращает исходный результат без новой записи. На конфликте клиент должен обновить очередь, а не менять решение автоматически. Запись запрещена без актуального назначения; школьные имена, идентификаторы авторов и статус нельзя передавать как доверенные поля.
- `plan_creation_requests` читается по RLS. Экран запрашивает только нужные для списка поля (`id,title,status,created_at`) и явно фильтрует выбранную школу. Состав заявок и маршруты других категорий не утверждены.

**Дальше:** подтвердить базовую матрицу в целевом облачном dev-проекте на синтетике; согласовать маршрут и требования к обезличиванию, прежде чем включать экран заявок вне локальной песочницы. Редактирование и удаление записей, делегирование, восстановление, офлайн-синхронизация, USB и production backup не реализованы.
