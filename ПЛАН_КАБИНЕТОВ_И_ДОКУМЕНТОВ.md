# SmartMaktab — план личных кабинетов и документов

> **Дополнение к объёму и порядку:** актуальный [справочник кабинетов школы, маориф и раёсата](СПРАВОЧНИК_КАБИНЕТОВ_ШКОЛА_МАОРИФ_РАЁСАТ.md) предусматривает отдельный HTML-файл для каждого направления и каждой предметной специальности. Он уточняет структуру папок и расширяет первый этап до создания каркасов всех запланированных кабинетов; три предметно разные формы ниже — примеры наполнения, а не ограничение числа страниц.

## Цель

Продолжить текущий SmartMaktab, не создавать приложение заново. При первом входе пользователь выбирает **школу → должность или назначение → заполняет данные для своей работы**. После подтверждения получает личный кабинет с подходящими разделами и шаблонами. Данные из профиля и реквизиты школы подставляются в документы автоматически; содержание пользователь проверяет перед сохранением и печатью.

## 2. Первый вход

1. **Школа.** Сначала выбор школы. В демо — вымышленные школы. В серверной версии — учреждения, доступные по приглашению или подтверждённой принадлежности; чужие списки сотрудников и данные не раскрываются.
2. **Должность или назначение.** Показать общий список в согласованном порядке. Школа может включать только применимые позиции. Если сотрудник совмещает роли, дополнительные назначения оформляются отдельно, без создания второго аккаунта.
3. **Данные для работы.** Показать только необходимые поля выбранной роли. Общие данные, которые повторяются в документах, заполняются один раз. Реквизиты школы берутся из настроек школы; рядовой сотрудник не изменяет их через свой профиль. Поля, для которых нет подтверждённой необходимости, не собирать.
4. **Подтверждение.** Выбор должности создаёт заявку. Пока назначение не подтверждено, можно просмотреть статус и собственный черновик заявки, но нельзя открывать защищённый кабинет или данные школы. Кто имеет право подтвердить каждую роль, согласуем отдельно; заявитель не подтверждает своё назначение сам.
5. **Рабочий кабинет.** После подтверждения видны должность, школа, задачи, документы и настройки профиля. Для совмещаемых подтверждённых направлений — переключатель рабочих разделов. При смене школы или отзыве назначения доступ пересчитывает сервер.

## 3. Что будет отличаться по должностям

Для каждой позиции согласовать одну карточку: **поля профиля → сведения для конкретного документа → шаблоны → кто проверяет/утверждает → кому доступно**. Сведения для отдельной формы (например, период отчёта или содержание плана) не нужно требовать при первом входе, если они нужны только при создании этого документа.

| Кабинет для первого прототипа | Пример полей профиля | Первый демонстрационный шаблон |
|---|---|---|
| Муаллим / Омӯзгор | Предмет, ступень, классы | План работы учителя |
| Мудири китобхона | Библиотека или подразделение; период указывается в документе | План работы библиотеки |
| Директор | Подтверждённое назначение; название школы подставляется из настроек | План работы учреждения |

Это предложения для проверки интерфейса, не утверждённые школьные формы. Точный набор полей не переносить из одного кабинета в другой. Профили психолога, бухгалтера и ученического самоуправления требуют отдельной проверки доступа и минимизации данных.

## 4. Как создаётся документ

1. Пользователь открывает свой кабинет и выбирает доступный шаблон.
2. SmartMaktab подставляет утверждённые реквизиты школы и нужные данные профиля; пользователь заполняет содержательные поля текущего документа.
3. Пользователь видит, какие данные подставлены и каких не хватает, проверяет результат и сохраняет **черновик** или открывает печатную форму. Черновик не является подписанным или утверждённым документом.
4. Если документ требует согласования, отправка на утверждение идёт по отдельному маршруту, который зависит от типа документа. Подтверждение должности и утверждение документа — два разных процесса.
5. Документ сохраняет собственный снимок подставленных реквизитов и версию шаблона: смена данных профиля не должна незаметно переписывать уже сохранённый или утверждённый документ.

## 5. Структура файлов: одна должность — одна HTML-страница

Главный `index.html` оставляем точкой входа и существующим демо. Он содержит ссылку на мастер первого входа, а не формы и кабинеты всех должностей. Новые экраны создаём отдельными файлами в том же проекте:

```text
SmartMaktab_App/
├── index.html                    # Главный экран и ссылка на первый вход
├── onboarding/
│   └── index.html                # Выбор школы и должности
├── cabinets/
│   ├── teacher.html              # Кабинет учителя и поля его рабочего профиля
│   ├── library-head.html         # Кабинет заведующего библиотекой
│   ├── director.html             # Кабинет директора
│   ├── class-teacher.html        # Рабочая страница классного руководителя
│   └── girls-council-chair.html   # Рабочая страница «Раиси Шӯрои духтарон»
└── shared/                       # Общий стиль, переводы, справочник, навигация и проверка доступа
```

Актуальные файлы разложены по уровням (`cabinets/school/`, `cabinets/maorif/`, `cabinets/raesat/`); точные пути приведены в справочнике выше. У каждой реализованной должности или назначения — собственный HTML-файл. Специфичную логику при необходимости выносим в соседний JS-файл, не добавляя её в главный `index.html`. Для разных кабинетов не дублируем меню, стили, переводы и общие проверки. Справочник ролей в одном месте хранит согласованный порядок и соответствие роли её странице. Для неподтверждённых направлений сохраняем место в справочнике и не придумываем формы или права.

Отдельный файл не является защитой: прямой переход по ссылке не должен раскрывать данные, если сервер не подтвердил школу и назначение. В демо раздельные страницы используют только вымышленные данные и явно показывают, что права не выдаются.

## 6. Этапы реализации и проверки

| Этап | Что делаем | Когда считаем готовым |
|---|---|---|
| 1. Первый вход в демо | В существующий `index.html` добавляем только ссылку. Сам мастер «Школа → Должность → Данные для работы» состоит из отдельной страницы входа и перехода на сайт выбранного кабинета. Сохраняем прежние экраны и переключение тоҷикӣ/русский. | Работают «Назад», смена школы, требуемые поля и экран «Ожидает подтверждения». Оба согласованных соседства в списке соблюдены. Только вымышленные данные. |
| 2. Первые три кабинета | Учитель, библиотека и директор: разные формы, разделы и первый шаблон. Для остальных — пункты в справочнике без выдуманных прав или шаблонов. | Учитель не видит поля библиотеки, библиотекарь не видит директорские действия; реквизиты школы подставляются, пробный документ печатается. |
| 3. Подтверждение и доступ | После проверки базовой облачной матрицы на синтетических аккаунтах проектируем серверные заявки, назначения, роли и RLS. Отдельно проверяем отзыв доступа, смену школы и несколько назначений. | Самовыбор не даёт полномочий даже при прямом запросе к API. Школа A не получает данные школы B. Смена назначения фиксируется в аудите. |
| 4. Остальные кабинеты и шаблоны | Проходим по справочнику по одному кабинету: согласовываем поля, обезличенные образцы, печатные формы и маршруты утверждения. | Для каждого включённого кабинета есть подтверждённый перечень полей, шаблонов и полномочий. |
| 5. Офлайн и синхронизация | Проверяем создание разрешённых черновиков без связи, повторную отправку без дублей и конфликты. Подтверждение полномочий и утверждение остаются серверными. | Черновик не теряется при сбое, не уходит в другую школу или аккаунт. Это отдельный этап, не функция первого демо. |

**Выполнено:** каталог из 54 отдельных страниц, три школьные формы (план урока учителя, месячный план библиотеки и годовой план директора), отдельные примеры мушовира по информатике и руководителя раёсата. **Следующий этап:** согласовать поля и правила назначения; прежде чем подключать реальные кабинеты, проверить облачную матрицу на синтетических аккаунтах. Серверные права и школьные данные на этом шаге не меняли.
