## Две полноэкранные заставки SmartMaktab

- При открытии стартовой страницы название SmartMaktab печатается по буквам на зелёной заставке с контурными кольцами. После выбора школы по «Оғоз» проигрывается другая заставка с линиями и названием выбранного МТМУ/должности. Затем открывается кабинет, порядок онбординга не менялся. Значок PWA не менялся.
- Обе заставки можно пропустить кнопкой или клавишей Escape. При системной настройке уменьшения движения запуск и переход не задерживаются. Анимации работают без сети в просмотрщике. Код/стили: `startup/brand-splash.{js,css}`; проверка `npm run test:brand-splash:browser`.

## Анкеты перед выбором школы и рабочие страницы

- Текущий порядок: уровень → основная/дополнительные должности → заполнение рабочих и персональных полей основной и дополнительных анкет → школа → «Оғоз» → готовый рабочий стол. Дополнительное назначение может иметь свою школу. Имя и фамилия подставляются из основной анкеты с возможностью правки; рабочие данные заполняются отдельно. Профиль директора, рабочие параметры учителя и профиль библиотеки открываются в анкете до выбора школы.
- В 54 отдельных кабинетах есть рабочий стол, настройки в шапке и навигация по документам/материалам. В боковой панели нет анкеты и выбора школы. Каждый кабинет содержит два демонстрационных шаблона и подсказки по работе; три специально реализованные формы (план урока, библиотеки и директора) подключены к соответствующим плиткам. Шаблоны не официальные и не полная библиотека документов.
- Выбор класса унифицирован: номер 1–11, затем буква кириллицы, включая буквы таджикского алфавита; в документе учителя доступен только класс из профиля этой школы. Переходы и карточки анимированы с учётом `prefers-reduced-motion`.
- Анкеты в этом прототипе синтетические; сервер, назначения и Supabase не менялись. Начальный перенос полей в кабинет одноразовый; коды школы, классы и рабочие настройки живут в рамках вкладки.
- Анимированные варианты иконки находятся в `SmartMaktab_Варианты_иконки.html` (три отдельных SVG в `icon-options/`). Значок приложения будет заменён после выбора пользователя.

## Текущая версия и ночной режим

- Публичный маршрут теперь один: старт → должности → анкета выбранной должности → поиск и выбор школы. Все 54 физические страницы имеют рабочую анкету, а в заголовках анкет указаны должности. Старые дашборд и каталог убраны из меню, автономной сборки и маршрутов рабочего предпросмотра. Их исходники сохранены отдельно от текущего интерфейса. Dev UI не публикуется в предпросмотре по умолчанию; тестовый запуск доступен только на loopback с `--with-dev`.
- Кнопка «Ночной режим» работает на старте и в кабинетах. В браузере выбранная тема сохраняется на этом устройстве; в автономном просмотрщике тема передаётся между открытыми кабинетами до закрытия файла. Печатный вид светлый.
- Проверено: 37 тестов, браузерные анкеты всех 54 должностей, переходы, светлая/ночная тема в браузере и в изолированном просмотрщике. Supabase не менялся.

## Кнопки в просмотрщике файла

- Исправление показа JS как текста: вложенная разметка строится через DOM, данные предпросмотра сжаты и не встраиваются как сырой HTML в тело JavaScript. Пометка о режиме просмотра скрывается после инициализации кнопок. Рабочий предпросмотр «SmartMaktab — рабочая версия» остаётся альтернативой, если оболочка просмотра не разрешает скрипты.

- Причина: встроенный просмотрщик блокирует внешние CSS/JavaScript и отправку HTML-форм. `npm run build:startup` собирает общий код и стили внутрь всех файлов кабинетов. Ключевые действия теперь обрабатывают кнопки напрямую и не ждут события нативной отправки формы.
- В `index.html` есть автономная копия всех 54 страниц: во встроенном просмотрщике «Оғоз» и переключатель должностей работают без сети, школы выбираются внутри открытого кабинета. В рабочем предпросмотре открываются обычные отдельные HTML-файлы.
- Кнопка «Печать» в просмотрщике показывает печатную версию с возвратом к форме; системный диалог доступен в рабочем предпросмотре. Состояние автономного показа хранится в памяти открытого файла, без сохранения анкет на сервере.
- Проверка: `npm run test:file-viewer:browser` использует sandbox `allow-scripts`, блокирует внешние запросы и проверяет прямой кабинет директора, старт, переход к дополнительной должности, школы и печатную версию.

## Все 54 кабинета · анкеты, школы МТМУ № 1–88 и боковое меню

- Обычный порядок: уровень → основная и дополнительные должности → общие имя/фамилия → «Оғоз» → анкета каждой должности в её физическом HTML → выбор школы. Старый каталог больше не публикуется. Прежняя директорская анкета сохранена; 53 остальные получили собственные рабочие поля (варианты для проверки, не утверждённые формы). В анкете ученического самоуправления нет личных и контактных полей.
- Список из 88 демонстрационных учреждений `МТМУ № 1`…`МТМУ № 88` ищется по номеру или названию. У учителя список мест работы также ищется и позволяет отметить несколько. У дополнительных должностей школа выбирается отдельно. Выбор не изменяет права и не расширяет показанные ранее области данных маориф/раёсата.
- Боковая панель закреплена при прокрутке; в каждом кабинете сворачивается кнопкой, один раз автоматически через 15 секунд и затем может открываться вручную.
- Рабочие формы живут в памяти страницы, не отправляются на сервер. Вкладка хранит коды выбранных демо-кабинетов/школ; синтетические имя и фамилия передаются одноразово с ограничением времени. Supabase не менялся. Файлы форм обновляются командой `npm run build:role-profiles` по `startup/role-profile-fields.txt`.

## Профили директора и учителя · контакты, курсы и несколько школ

- В анкету директора добавлены необязательные телефон, почта, адрес, пол и достижения: «Аълочии маориф», «Ифтихорнома», денежная награда или другой вариант. Можно отметить несколько и указать детали. Паспортные поля не добавлены.
- Курс имеет название, организатора, даты начала и окончания, состояние «Завершён»/«Запланирован». Демо-интервал — 3 года от даты окончания последнего завершённого курса; запланированные не сдвигают срок. Для 29 февраля берётся последний день февраля целевого года. Это заданная настройка прототипа, не утверждение официальной нормы. Контакты, награды и курсы только в памяти страницы, без отправки и попадания в план.
- В кабинете учителя галочками выбираются несколько вымышленных школ. Список выбранных школ хранится в текущей вкладке. После перехода профиль классов и языка берётся только для активной школы, документы не объединяются. При уходе в другую должность из дополнительной школы используется исходная школа её кабинета. Выбор не подтверждает назначение.
- Проверено: `npm test` 35/35; 7 сценариев Chromium, в том числе контакты, награды, дата окончания курса и отдельные школьные профили учителя. Supabase не менялся.

## Вход в основную должность и анкета директора

- На финальном экране вместо повторной регистрации — **«Оғоз»**. Кнопка открывает физическую HTML-страницу основной должности. В её верхней панели есть «Мои кабинеты» только при наличии выбранных дополнительных ролей; список из текущей демо-сессии и той же вымышленной школы сохраняется в рамках вкладки. Ссылки на посторонние уровни убраны из боковых меню всех 54 должностей.
- **Анкета директора** отделена от реквизитов учреждения и плана: ФИО (отчество при наличии), год рождения, стаж в образовании и стаж директором, языки со свободным вариантом «Другой», вуз, специальность, уровень диплома, примерные категории и год последней аттестации. Годы окончания вуза и назначения необязательны; повышение квалификации вынесено в отдельный раздел курсов. Паспортные данные не запрашиваются. Валидация: стаж директора не больше стажа в образовании, годы не выходят за допустимые рамки.
- Для синтетических анкет имя и фамилия переносятся через одноразовую запись вкладки, действительную пять минут; запись удаляется при чтении своим кабинетом. Анкета директора остаётся в памяти конкретной страницы и не включается в годовой план; после ухода или перезагрузки не восстанавливается. Сервер и права доступа не менялись.

## Старт SmartMaktab · выбор до 11 кабинетов

- Новый `index.html` показывает **Раёсат → Маориф → Муассиса** как три варианта первого шага. Порядок после выбора: одна основная должность → до 10 дополнительных на том же уровне → анкета основной → проверка дополнительных → кнопка «Оғоз» и переход в основной кабинет. У «Муассиса» доступны все 20 школьных пунктов в прежнем порядке; актуально: вымышленная школа теперь выбирается в каждом кабинете после его рабочей анкеты.
- Имя и фамилия по отдельности наследуются из основной анкеты. Индивидуальные правки других должностей не затираются при изменении основной анкеты; их можно сбросить к основным значениям. Должности нельзя дублировать. Профили работы и документы остаются на собственных страницах.
- В мастере используйте вымышленные данные. Выбранные кабинеты хранятся в рамках вкладки, а имя и фамилия для анкеты директора передаются одноразово. В URL нет имён (там только демо-школа и язык). Это не подтверждение назначения и не авторизация. Supabase не менялся.
- Прежнее демо сохранено в `dashboard.html`. Стартовый файл собирается командой `npm run build:startup` из `startup/` и реестра кабинетов, не использует сетевые ресурсы для работы формы в просмотрщике. `npm test` — 33/33, `npm run test:startup:browser` — два сценария, включая sandbox без сети.

## Кабинет директора · профиль и годовой план

- `cabinets/school/director.html` — отдельный кабинет. Название и демо-код берутся из выбранной школы. В профиле — тип учреждения и сменность. В черновике — учебный год, цель, список задач с направлением, месяцем и ответственной должностью.
- Сроки проверяются с сентября по август; печатный список сортируется по месяцам. Правки не переписывают сформированный черновик, а сроки вне нового учебного года отмечаются. Профиль хранит только допустимые коды по школе в текущей вкладке; план после перезагрузки исчезает.
- Проверено: `npm test` (32 теста) и сценарии Chromium для директора, библиотекаря и каталога/учителя. В каталоге 5 страниц с примерами и 49 каркасов. Назначений, согласования и отправки в маориф нет, Supabase не менялся.

## Кабинет библиотекаря · месячный план

- На отдельной странице `cabinets/school/library-head.html` профиль задаёт рабочую зону и разделы фонда. В план на месяц можно включить до 12 мероприятий с аудиторией. Фонд в каждом мероприятии выбирается только из профиля.
- Профиль сохраняет только разрешённые коды в `sessionStorage` для выбранной вымышленной школы. Рабочий список и печатный черновик после перезагрузки не сохраняются. При смене профиля прежний черновик не переписывается; рабочие строки из снятого раздела отмечаются. Supabase и форма учителя не изменены.
- Проверено: `npm test` (30 тестов), `npm run test:library:browser` и регрессионный Chromium для каталога и кабинета учителя. Демо содержит четыре наполненных страницы и 50 каркасов.

## Кабинет учителя · профиль и план урока

- На отдельной странице `cabinets/school/teacher.html` профиль и документ разделены. После выбора вымышленной школы учитель задаёт классы и язык обучения; информатика — фиксированный предмет примера. Для каждого плана выбирается один из классов профиля и указываются дата, тема и цель.
- Профиль содержит только разрешённые коды и хранится в `sessionStorage` текущей вкладки отдельно для каждой демо-школы. Печатный черновик живёт в памяти страницы; изменение профиля не переписывает уже сформированный черновик. Нет отправки в маориф, реальных данных или изменений Supabase.
- Проверено: `npm test` (28 тестов) и `npm run test:cabinets:browser` (выбор классов, печатный вид, восстановление профиля после перезагрузки и изоляция демо-школ). Код формы вынесен из общего файла в `teacher.mjs` и `teacher-data.mjs`.

## Этап 0.6 · локальная очередь IndexedDB

- В localhost-песочнице за вторым выключенным по умолчанию флагом добавлена очередь синтетических заявок на план. Можно сохранить заявку без сети, заново войти с сетью и отправить вручную. Очередь разделена по адресу API, аккаунту и школе; незашифрованная IndexedDB не предназначена для школьных данных. Auth и решения директора в неё не пишутся.
- Перед отправкой сохраняется UUID и исходное название. Сценарий Chromium проверяет потерю сети, перезагрузку, изоляцию аккаунтов, потерю ответа после коммита и повтор без дубликата на реальном локальном Supabase Auth/PostgREST. Контрольные проверки базового dev и эксперимента согласований также проходят.
- Облачная привязка, межустройственная синхронизация и офлайн-вход не реализованы. См. [OFFLINE_OUTBOX_EXPERIMENT.md](OFFLINE_OUTBOX_EXPERIMENT.md).

## Этап 0.5 · интерфейс согласования в локальной песочнице

- В существующем `dev/` добавлен двуязычный экран создания и рассмотрения заявки на план. Он требует `approvalExperiment: true` и локальных адресов страницы и API; базовый и облачный Dev остаются только для чтения. Основной PWA-прототип остаётся отдельным демо.
- Список зависит от текущей школы и роли, RLS и серверные RPC проверяют доступ независимо от UI. При неизвестном результате повтор использует те же параметры и тот же ключ. В режиме 0.5 без опции очереди черновики и ключи повтора не сохраняются после выхода или перезагрузки.
- Прошли 21 локальный тест, базовые `test:live` и `test:browser:live`, а также API- и браузерный сценарии согласований на реальных локальных Supabase Auth, PostgREST и PostgreSQL. Для проверки повтора Chromium терял первый ответ после выполнения RPC: повтор не дублировал заявку или план.
- Облачной привязки, согласованных школьных полномочий, пагинации заявок и офлайн-очереди пока нет. Порядок запуска — [PLAN_APPROVAL_EXPERIMENT.md](PLAN_APPROVAL_EXPERIMENT.md).

## Этап 0.4 · эксперимент согласования

- Отдельный opt-in SQL реализует только заявку на создание плана: сотрудник/завуч подаёт, директор той же школы принимает решение, подтверждённый план создаётся атомарно. Тестовый маршрут не является утверждённой школьной политикой. Базовая миграция не изменилась и не включает запись.
- Проверены неизменность заявки из клиента, изоляция школ и очереди, запрет самоутверждения и записи напрямую, отзыв прав, защита от дублей и откат. Прошли 20 локальных тестов (7 новых), базовые `test:live` и `test:browser:live`, а также экспериментальный `test:approval:live` на реальных локальных PostgreSQL 17.11, Supabase Auth и PostgREST, включая параллельное утверждение и гонку противоположных решений.
- На этапе 0.4 интерфейс ещё отсутствовал; с 0.5 доступен только на локальном стенде. Как повторить эксперимент на синтетической базе: [PLAN_APPROVAL_EXPERIMENT.md](PLAN_APPROVAL_EXPERIMENT.md).

## Этап Supabase Dev · сквозная проверка локально

- Миграция применена к PostgreSQL 17.11; проверка прошла через настоящий Supabase Auth (GoTrue v2.198.0) и PostgREST v16.6 с подписанными токенами. Проверены шесть синтетических аккаунтов: сотрудник, завуч, директор, маориф, разработчик и пользователь без назначения. Для школьного администратора дополнительно действует локальный SQL-тест.
- Подтверждены отказ anon, неверный пароль, изоляция школ и зон, запрет клиентских изменений и чтения закрытых полей, отзыв refresh-токена при выходе. На том же JWT после удаления назначения сервер перестал отдавать данные; в аудите зафиксирован `DELETE`.
- Chromium без подмены API: проверены вход, переключение доступных школ, скрытие чужой школы, отсутствие данных у аккаунта без назначения и очистка данных при выходе.
- Добавлены `supabase/config.toml`, `npm run test:live` для локальной/облачной приёмки и `npm run test:browser:live` для loopback. Прежние 13 локальных тестов и браузерный тест с подменой HTTP по-прежнему проходят.
- **Облачный проект не привязан.** Полный набор контейнеров Supabase CLI здесь не запускался. Следующий шаг — прогон на пустом целевом dev-проекте по [инструкции](SUPABASE_DEV.md), не на школьных данных.

## Этап Supabase Dev · подготовка

- Сохранён существующий PWA. Из меню открывается отдельный двуязычный `dev/`, где реализован вход по email/паролю через Supabase Auth и чтение списка учреждений/записей через Data API. Без публичной конфигурации вход недоступен. Токены и облачные данные не сохраняются в хранилищах демо.
- Добавлена первая миграция для пустого dev-проекта: серверные роли и RLS из БД, доступ только на чтение, запрет записи всем клиентским ролям; отдельный список разработчиков, аудит доверенных изменений. `supabase/schema.sql` оставлен как история, не применять.
- Проверено локально: 13 автоматических тестов (PGlite и валидатор конфигурации), тест Chromium с подменой ответов Auth/Data API, сборка клиента и синтаксис JS. Данные во всех тестах синтетические.
- **Не подключено к облачному Supabase.** Сквозные проверки с реальным Auth/Data API выполнены локально; проверка в целевом проекте ещё впереди. Read-only — сознательное ограничение до согласования прав и маршрутов утверждения; серверная корзина в части восстановления, аудит чтения и production-готовность не заявлены.
- Следующий шаг: [SUPABASE_DEV.md](SUPABASE_DEV.md) — развернуть в пустом dev-проекте и подтвердить матрицу доступа на синтетических аккаунтах. Реальные школьные данные не нужны до согласования безопасности и обезличивания.

## Уже реализовано в браузерном прототипе
- Главная панель и разделы сотрудников, документов, планов/поручений, заседаний, согласований, источников, настроек.
- Переключение таджикский/русский; дневная/ночная темы.
- Добавление демонстрационных сотрудников, документов, задач, заседаний и источников.
- Статусы выполнения поручений и принятия/отклонения запросов.
- Локальное сохранение и разделение демонстрационных данных по селектору школы в браузере.
- Экспорт/восстановление зашифрованной локальной резервной копии (AES-GCM-256, PBKDF2); старый JSON импортируется только с предупреждением и подтверждением. Это ручная локальная копия, не автоматическая Supabase/GitHub backup.
- Отдельное локальное хранилище по каждому выбранному учреждению (демо-уровень).
- Журнал локальных действий: создание, утверждение/отклонение, перенос в корзину, восстановление и смена учреждения.
- Корзина с полным снимком демонстрационной записи и возможностью восстановления (не удаляется сразу безвозвратно).
- PWA manifest и кеш оболочки для повторного открытия офлайн после загрузки.
- Для PWA добавлена проверка онлайн-обновления с уведомлением и кнопкой перезапуска (Service Worker waiting flow). Это веб-обновление, не USB-передача Android → Windows.
- Начальный SQL-скелет Supabase с организациями, членством, записями, запросами на утверждение, аудитом и RLS.

## Не реализовано и не должно считаться готовым к реальной школе
- Привязка и проверка реального облачного Supabase-проекта; клиент Auth подготовлен отдельно.
- Проверенная безопасность/изоляция многопользовательских данных и ролей в боевой среде.
- Синхронизация локальных изменений между устройствами и разрешение конфликтов.
- Реальные правила утверждения записей, настраиваемые по роли/категории и юридически проверенные.
- USB-передача/установка полного обновления Android → Windows; нужен нативный мост или устанавливаемая Windows/Android-оболочка, чего браузерный прототип сам не обеспечивает.
- Резервное копирование Supabase в GitHub. Нельзя отправлять секреты или незашифрованные персональные данные в Git. Нужны приватный зашифрованный backup, отдельная политика хранения и проверенное восстановление.
- Реальные школьные шаблоны и поля; ожидаются обезличенные примеры пользователя.
- Аудит чтения, политика retention, серверное восстановление и сквозные тесты на целевом Supabase (триггеры записи и локальные тесты добавлены).

## Порядок перед пилотом
1. Развернуть отдельный Supabase Dev и проверить Auth/SQL на тестовых аккаунтах; использовать только публичный ключ в клиенте.
2. Согласовать безопасность, обезличивание и маршруты утверждения до получения школьных данных.
3. Подключить контролируемые серверные операции записи и дополнить аудит.
4. Реализовать durable offline store, очередь синхронизации, version checks/conflict UI и тесты потери сети.
5. Сделать proof-of-concept USB: Windows app/helper + Android sender, цифровая подпись, проверка версии/целостности, rollback при ошибке; проверить user flow.
6. Добавить тесты и процедуры backup/restore; провести security review.
7. Пилотировать только на синтетических/обезличенных данных; после приемки — школа с минимально необходимыми правами.

- `.github/workflows/signed-release.yml`: ручной выбор одного EXE/APK/AAB; подписанные production-сборки, проверка ключей, подписей и SHA-256 до выдачи артефакта. Без автоматической публикации и отладочного режима. `РЕЛИЗ_НА_GITHUB.md` — секреты владельца, сборка и проверка.
- Electron и Android WebView упаковывают публичный интерфейс; не включают Dev-проект или реальные ключи. Веб/PWA/portable сохранены. Проверка на реальных Windows и Android после первого подписанного прогона обязательна.
- Учитель: подходящие учебники выше рабочих разделов; настройки содержат школу, классы и предметы. Алия в телефоне — полноэкранный экран по Kitobkhona с контекстом, шестью задачами, листами настроек и последовательными карточками результатов. Локальный режим ограничен текстом PDF; точное визуальное и функциональное равенство оригиналу не заявляется.
- Входной ZIP шаблонов: парная проверка без импорта; права и утверждение не подтверждены. Облачный Dev и шлюз Алии не публиковались.
